# WCN7850 on Windows 11 ARM64

## First experiment, 2026-11-24

Upstream revision: 2a2a50f. The connected adapter was a Qualcomm FastConnect 7800
(PCI 17CB:1107) on Windows 11 Pro ARM64 build 26300.

With the station connected, run:

```powershell
netsh wlan show drivers
netsh wlan show wirelesscapabilities
python -B -m unittest discover -s tests -p test_awdl_tcp.py
```

The installed driver was 1.0.4374.1300, reporting WiFiCx 1.2 and firmware
WLAN.HMT.1.1.c5-00310. It advertised action frame support and Wi-Fi Direct.
It reported network monitor mode, promiscuous mode and the IHV extensibility
module as unsupported. These are capabilities reported by the installed
Windows driver. They do not establish whether the firmware can exchange
AWDL frames while associated.

All five upstream TCP coalescing tests passed. They use synthetic packets.
No AWDL peer discovery, over-the-air frame exchange or file transfer has
been demonstrated. The upstream driver INF matches an AMD64 MediaTek PCI
device. A driver for this machine must target ARM64 and the Qualcomm hardware.

The next experiment is to identify a documented receive interface for
AWDL vendor-specific action frames with the station connected, then verify
reception with a known Apple peer on the same channel.

## Device service notification experiment

With all five advertised services subscribed, the 90-second run produced

The host registers the Microsoft-Windows-NWiFi and Microsoft-Windows-WLAN-Driver
ETW providers. A search of their event descriptions and templates for action
frames, management frames or frame-body fields found no explicit match.
This metadata check did not capture radio traffic. A useful next observation
would require a confirmed source of raw 802.11 management frames and a
known transmitting peer on the observed channel.

## WCN7850 cross-check against Owly

[Owly PR 103](https://github.com/t4t5/owly/pull/103) documents 96 iPhone
AWDL frames on WCN7850 with firmware WLAN.HMT.1.1.c7-00108. In a
monitor-only experiment the receive path appended a valid four-byte FCS
without setting the radiotap flag. Checking the CRC before stripping the
FCS let the parser recognize the peer. The same report found peer frames
absent on the monitor alongside an AP or station, and monitor-only TX
dropped by that Linux driver. The merged change addresses parsing only.

[The separate driver-patch report](https://github.com/t4t5/owly/issues/40#issuecomment-6547036843)
claims shared and exclusive operation. Its [attached run](https://github.com/user-attachments/files/34222921/owly-test-ath12k_wifi7_pci-1793468053.json)
records channel 6, exclusive mode, kernel 7.3.0-4-cachyos and passes for
both transfer directions. The route baseline was skipped. The shared-mode
claim has no corresponding run in that attachment. The exact kernel diff
used in that run has not been verified.

[Qualcomm's monitor support series](https://lists.infradead.org/pipermail/ath12k/2025-April/006823.html)
documents monitor status and destination rings and their interrupts. It
provides a chip-level reference. Its relationship to the working Owly
kernel patches has not been established.

For the Surface, require a full received management frame with its length
and body before applying any FCS handling. WlanLogger currently supplies
classification evidence. Then verify that the iPhone can observe a
response and test concurrent station operation separately.

## Action frame indications on the installed Qualcomm Windows driver

Offline inspection of the three WlanLogger traces found 2, 10 and 10
WdiSendIndication records for ACTION_FRAME_RECEIVED in the scan, picker
and BLE runs respectively. Every reported status buffer length was 82
bytes. In the scan trace the driver classified category 5/action 0, logged
its indication on 5220 MHz and reported completion. These traces expose
the status size and classification. The 82 bytes include indication
metadata and cannot be interpreted as an 82-byte wireless frame body.

[Microsoft's indication contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/netcx/ndis-status-wdi-indication-action-frame-received)
specifies source BSSID, channel information and WDI_TLV_ACTION_FRAME_BODY.
The contract is between the client driver and WiFiCx. The inspected
Windows event templates did not expose an explicitly named indication
buffer or action frame body. An OEM
[device service](https://learn.microsoft.com/en-us/windows-hardware/drivers/netcx/oid-wdi-get-supported-device-services)
would need a documented service contract exposing equivalent bytes.

A Windows proof of concept should first obtain the body of one of the
recurring category-5/action-0 frames through a supported interface. Peer
discovery and category-127 forwarding are separate tests after this
positive control. No new phone or router experiment is needed for this step.

## Native ARM64 offline receive replay

Run scripts/Test-SurfaceArm64Replay.ps1 on the Surface. It builds src/rx.c
as an ARM64 kernel-mode object, links that same object into the user-mode
test executable and replays three pinned Owly channel-44 captures using
the upstream assertions. Both machine headers were ARM64 (0xAA64).
Discovery, receive and send captures passed with 1229, 5413 and 2731
frames respectively. These files were recorded on an MT7925e. The

802.11 frames. A WCN7850 backend must supply those bytes independently.

## WCN7850 WMI management receive envelope replay

The offline reader takes a WMI event including its command header and
returns a borrowed frame view, firmware status and frequency. The layout
follows the [ath12k v6.16 definitions](https://github.com/torvalds/linux/blob/v6.16/drivers/net/wireless/ath/ath12k/wmi.h).
The Surface replay wrapped 4,893 recorded PSF/MIF frames in synthesized
management receive events. For each it tested both fixed-header-first
and byte-array-first order, byte equality, classification, and rejection
of truncation, missing metadata, an excessive declared length and a wrong
event ID. The enclosing firmware bytes were simulated. Local verified
captures can be supplied with -CaptureDirectory to avoid downloading again.

A separate search in the existing joint ETL found 146 event payloads
mentioning WMI_MGMT_RX_EVENTID. None contained the contiguous command
header, 68-byte fixed TLV and complete frame array in the common order
checked. Other representations and split events remain possible.

### Directed LAN discovery experiment

With the iPhone paired over USB, use a Python environment containing
pymobiledevice3 (tested with 11.63.1) and OpenSSL available to the receiver:

```powershell
$localIPv4 = (Get-NetIPAddress -InterfaceAlias WLAN -AddressFamily IPv4 |
    Where-Object AddressState -eq Preferred | Select-Object -First 1).IPAddress
python -B scripts/probe_iphone_lan_discovery.py --ipv4 $localIPv4
```

Reopen Photos > Share > AirDrop when the script prints its ready message.
The script reads the phone's en0 mDNS questions over USB and replies on
WLAN by unicast to the phone. The receiver binds its TLS socket to the WLAN
link-local IPv6 address and allows phone link-local addresses observed in
outgoing en0 traffic. It serves the original /Discover response with the
name Surface-Test. /Ask and /Upload are refused. The DNS records expire
after ten seconds. No firewall rule is installed. This experiment cannot
determine whether iOS would treat multicast announcements the same way.

Three Surface-originated queries with a random label calibrated incoming
pcapd direction 16 on this phone. The probe uses direction 1 for outgoing
packets. The DNS parser covers UDP over ordinary IPv4 or IPv6 headers on
en0. Fragment reassembly and IPv6 extension headers are outside this probe.

In a picker run with a single USB capture session, 20 outgoing en0
queries and seven awdl0 queries asked for the AirDrop service type. The
receiver matched 22 en0 queries across its service, instance and host
names. It sent 16 unicast replies after rate limiting, and all 16
responses were observed on the phone's en0 interface with the test
instance name. The probe counted no TCP SYN to the advertised link-local
IPv6 endpoint and logged no /Discover request. The operator saw no
Surface-Test entry. This establishes delivery of these DNS responses but
does not establish that iOS accepted them for its AirDrop browser.

In a separately authorized 60-second IPv6 multicast run on the same
WLAN, the Surface sent 30 positive announcements and one goodbye.
The phone logged 27 inbound DNS responses naming the test instance on
en0 during observation. It issued ten AirDrop service queries on en0 and
four on awdl0. No matching TCP SYN or /Discover request was recorded, and
the operator again saw no Surface-Test entry. This run used the upstream
DNS record builder, periodic announcements, short TTLs and a discovery-only
TLS endpoint. It did not exercise an AWDL radio link on the Surface.

## Copy-engine completion to management-frame replay

In the [pinned WCN7850 reference](https://github.com/openbsd/src/blob/70422bd0fb62822e7aeb280535affaab1719f650/sys/dev/ic/qwz.c#L21186),
the copy-engine receive callback checks the completed byte count and hands
that buffer to the pipe's receive handler. HTC dispatches to the endpoint
negotiated for the WMI service. The WMI event ID starts immediately after
the eight-byte HTC header; an optional HTC trailer is outside the WMI
event. The endpoint number must come from the service connection response.

The ARM64 replay now also passes the 4,893 captured AWDL action frames
through synthetic HTC messages, both with and without a trailer. It checks
the borrowed frame location and rejects mismatched endpoints, truncated
completions and inconsistent trailer lengths. A live Windows producer must
supply a completed buffer, its actual byte count and its negotiated WMI
endpoint, and keep the buffer alive while the frame is in use. The replay
does not own a PCI device or receive DMA completions.

## Complete management frames recovered from WlanLogger text

The startup ETL contains a second representation: a labelled
`ieee80211_dump_mgmt_pkts` record followed by consecutive `OL:` hex
rows with byte offsets. The new `scripts/check_wcn7850_text_frames.py`
reader requires contiguous offsets, agreement with the declared length
and a matching frame-control subtype. It reports counts and lengths only.

Seven complete dumps were reconstructed in the restart trace. Three
were labelled receive: authentication (30 bytes), association response
(283 bytes) and probe response (486 bytes). Starting after their fixed
fields, the association and probe responses contained 15 and 23 information
elements respectively, both ending exactly at the declared frame boundary.
The other four were three sends and one candidate probe response. None
was an action frame. The same reader found no complete labelled dumps in
the other 14 ETLs. This establishes byte-level receipt for the three
observed management subtypes; it does not establish action-frame delivery.

All 33,138 WlanLogger payloads in the startup ETL had ASCII text followed
by NUL and no nonzero trailing data. No complete binary action-body TLV
matching the logged category/action pairs was found. Keep raw startup
traces local: unrelated diagnostic hex dumps include key-install records.

### Why the labelled dumps can differ from the action indications

An independent pass over the saved traces reassembled consecutive WlanLogger
`OL:` hex rows starting at offset zero without requiring a preceding
management label. The restart ETL contained 67 such groups. They included
all seven previously validated management dumps. None contained a header
matching the destination, sequence field, category and action of any of
the four startup classifications. The same per-trace header search and a
search for the five-byte AWDL prefix returned no matches in reconstructed
groups from the other 14 ETLs. This check is limited to the observed row
syntax and contiguous offsets.

Read-only inspection of the installed ARM64 driver (1.0.4374.1300, SHA-256
`ca884ce1a22113194f3c467f36abc39afb0c137e5a7a8e2697420438b21e4115`)
found a dump routine referencing `ieee80211_dump_mgmt_pkts` whose direct
callers reference receive, send and scan function names. One branch in
the routine calls a helper referencing `stac_is_connecting` and skips
the dump when that helper returns false. A different branch bypasses that
check. This makes connection-state-dependent logging plausible; the active
branch during each recorded indication is unknown.

The driver also contains the UTF-16 string `DumpTxRxManagementFrame`.
The active adapter's class key had no value of that name, its Ndi
advanced-property definitions did not include it, and no installed INF
searched declared it. The string alone does not establish how it is read
or whether it controls action-frame dumps. No setting was changed.

On the same driver build, the name pointer at RVA `0x333e40` belongs
to entry 294 (zero-based) in a table of 72-byte descriptors starting
at `0x32ebd0`. A separate directory at `0x2f59b0` points to the table
and supplies a count of 306. The entry gives offset `0x186c` and a
one-byte width. The entries on either side name `WfdExcludeUnencryptedSAP`
and `addBaSize`.

The initialization code at `0x170998–0x1709a8` copies `0x1888` bytes to
object offset `0x34920`. Adding the entry offset gives `0x3618c`, exactly
the byte read by the management dump routine at RVA `0x93488`. This
links the setting to the logging decision. With value 1 the branch checks
the connecting state. Value 2 skips that particular check. Registry
scope and the effective runtime value remain unverified. The logging
branch alone gives no evidence of AWDL frame delivery or transmission.

Tracing the table reader resolves the registry scope. In
`MpReadRegistryConfiguration`, RVA `0x3d408` opens the device's driver
software key (KMDF slot 48, key type 2, access `0x20019`).
The loop at `0x3d4a0` passes that handle and each descriptor table to
`0x3dab8`. For this entry, the call at `0x3dbcc` queries a DWORD by
name on the same handle (KMDF slot 240, `WdfRegistryQueryULong`).
At `0x3dfdc` a failed query or a value outside 0 through 2 selects
the descriptor default of 1. The helper stores one byte at `0x3e608`.
The present FastConnect 7800 device's driver key resolves to network
class instance `{4d36e972-e325-11ce-bfc1-08002be10318}\0000`.
A read-only check found the value absent. This establishes what this
initialization path selects, without observing live driver memory.

Two 12-second WlanLogger samples on the connected Surface tested the
setting. With the value absent, 21,111 logger records contained one
action indication and zero complete labelled management frames. With
DWORD 2 after an adapter restart and reconnection, 33,018 records yielded
119 complete frames. The existing contiguous-row parser validated 115
received beacons and four action frames. Both directions had complete
bodies: category/action pairs were 19/4 and 5/4 on send, 19/5 and 5/5 on
receive. None matched the AWDL action signature. This validates the
capture method for ordinary action frames on this Windows driver build.

With the iPhone AirDrop recipient picker open, a separate 20-second
mode-2 trace contained 36,640 logger records and 191 complete received
beacons. There were zero action indications and zero complete action
frames. All 191 beacons advertised primary channel 44, as did the 115
control beacons. The beacon fields do not measure dwell on other
channels. After capture the temporary value was removed, the adapter
was restarted, and both value absence and WLAN link-up were verified.

The firmware management-RX metadata in that 20-second picker trace
reported 5220 MHz on all 195 records. It contained no accepted
`WMI_SCAN_EVENT_FOREIGN_CHANNEL` notification. A separate explicit
scan trace (`SurfaceWlanLog-a8ca6858…`) reported visits to 2437, 5220
and 5745 MHz among 26 distinct frequencies. Six management-RX records
reported 2437 MHz, and six beacon receive records reported channel 6.
There was no management-RX record at 5745 MHz in that trace. The earlier
`SurfacePickerJoint-2d87059c…` trace also reported all three scan
frequencies, with management RX at 2417 and 5220 MHz only. Scan visits
by themselves supply neither dwell duration nor evidence of AWDL reception.

Two further 25-second mode-2 samples each included one completed Windows
WLAN scan. Both reported visits to 26 distinct frequencies. The control
contained 251 complete frames (226 beacons, 15 probe responses, five sent
and five received action frames). With the iPhone recipient picker open,
243 complete received frames comprised 230 beacons and 13 probe responses.
Three probe responses advertised channel 6. No complete action frame or
classified incoming action appeared in the picker sample. Neither sample
had management-RX metadata at 5745 MHz. The picker scan's channel-149
and channel-6 notifications preceded the next channel notification for
that scan by 19.8 ms and 8.8 ms respectively (host event timestamps).
The picker was open for the scan, but its duration is not a measure of
radio time on either channel. The temporary value was removed and WLAN
link-up was verified after the second restart.

### Timed Wi-Fi Direct listen windows with the station connected

A 12-second Windows Wi-Fi Direct advertisement with intensive
discoverability, autonomous GO disabled and legacy mode disabled reached
Started and then Stopped. The driver completed the set-listen-state OID
on enable and disable. It requested 175 ms listen periods at a 300 ms
interval with one active station. There were 34 paired on-channel start
and end notifications at 2462 MHz (channel 11). Their host timestamp
separations were 175.4–176.8 ms, median 176.1 ms. In the whole trace,
firmware management RX reported 112 records at 2462 MHz and 166 at
5220 MHz. A P2P probe-request log explicitly reported both receive and
listen frequency as 2462 MHz. WLAN was up after stopping.

The WinRT advertisement object on this host exposes discoverability but
no listen-channel property. This run establishes repeated off-channel
reception under Windows. Selection of an AWDL channel and delivery of
AWDL frames during those windows remain unverified.

The installed Qualcomm driver's configuration table contains a DWORD
keyword named `WfdListenChan` (descriptor RVA `0x330f40`, byte offset
`0x106`, default 11). The value is absent from the active adapter's
driver key. At `0xd51f4` P2P initialization reads object offset
`0x34a26`, equal to configuration base `0x34920` plus `0x106`.
It converts the channel with operating class 81, checks the resulting
frequency against 2412, 2437 and 2462 MHz, and falls back to channel
11 on a miss. The listen-channel setter at `0xd6ad0` also checks
channel number against mask `0x842` (1, 6, 11). Thus 6 is a candidate
for a reversible test of this specific driver path.

The host can separately supply an optional channel in the WiFiCx
set-listen-state request. The driver's parsed request tests a presence
bit at `0x4ab20` before calling the setter wrapper at `0x4ab30`.
The previous trace identifies the resulting frequency but does not show
whether the host supplied a channel. A runtime test must verify actual
on-channel notifications after changing the default.

With `WfdListenChan=6` and `DumpTxRxManagementFrame=2`, the connected
Surface entered 34 listen windows on 2437 MHz during a 12-second control
and 70 during a 25-second intensive Wi-Fi Direct advertisement after

175 ms. During the picker sample, firmware reported 308 management
receives at 2437 MHz and 229 at 5220 MHz. Reassembled frames included
302 beacons advertising channel 6, 220 advertising channel 44, two

5220 MHz. No complete action matched the AWDL signature. The user
reported that the picker quickly showed no recipients. Capture began
after confirmation and did not cover the instant the picker opened.
Both temporary values were removed and WLAN link-up verified.

A follow-up started the publisher and ETW before prompting the user to

00:01:16.799 local time on November 25. The publisher was confirmed active

### iPhone-side channel evidence over paired USB

An iOS unified-log stream started before the user was prompted to open
the AirDrop picker and continued through their acknowledgement. Across the
whole window, 1,441 message bodies mentioned AWDL. Messages whose text
or logging label referenced AWDL contained each of the numeric field
strings “channel = 6”, “channel = 44” and “channel = 149” six times.
The parallel IORegistry query found the AirLink role in 104 samples
without a numeric channel hint. A separate 18-second stream observed
an awdl0 AWDL Channels message listing 149, 44 and 6, and separate
setChannelSequenceUnconditional schedule messages. The sampling pass
retained keywords and counts, not a decoded slot sequence. A subsequent
65-second narrow filter returned no matching schedule message. These
observations establish the phone listed the three channels, but identify
neither per-slot occupancy nor the transmit channel of any AirDrop frame.

A synchronized run captured the confirmed picker opening on November 25.
The phone reported sending an AWDL ON schedule to its Radio Resource
Manager. Three availability-table messages received over USB between
the Surface prompt marker and the user's acknowledgement contained the
same eight-byte bitmap for each channel:

| Channel | Bitmap bytes in logged order | Set bits |
| --- | --- | ---: |
| 6 | `00 00 00 00 0f 00 00 00` | 4 |
| 44 | `ff 00 00 f0 f0 f0 00 f0` | 24 |
| 149 | `00 0f 00 00 00 0f 00 00` | 8 |

Windows reported 541 management receives at 5220 MHz and 11 incoming
category-5/action-0 classifications there. The closest channel-44
management RX to each USB message's host arrival was 24, 50 and 2 ms

observation that the Surface received an AWDL frame.
